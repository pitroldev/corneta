## The status map

| Status            | What's happening                                  | What to do                                                       |
| ----------------- | ------------------------------------------------- | ---------------------------------------------------------------- |
| **Waiting**       | Corneta hasn't received a signal yet              | check the address and start streaming in your streaming software |
| **Connecting**    | the output is opening a session with the platform | wait; if it doesn't change, test the key and server              |
| **LIVE**          | the platform is receiving media                   | keep an eye on bitrate and dropped frames                        |
| **Reconnecting**  | the output dropped and is trying to come back     | investigate only the affected destination                        |
| **Paused**        | you stopped that destination                      | use **Resume** when you want it back                             |
| **BE RIGHT BACK** | the protection screen replaced the signal         | check whether it was a manual pause or OBS dropping out          |
| **Error**         | the attempt stopped with a known cause            | open the message and use **Try again** after the fix             |

## The platform confirms it too

With your Twitch, Kick or YouTube account connected in Corneta, a destination that's **LIVE** gets a line with what the platform itself sees:

- **"Twitch confirms you're live"**: the live shows up on the connected account's channel.
- **"YouTube confirms you're live but warns: …"**: the live arrived, but the platform recommends a change, such as a 2-second keyframe interval. The live carries on, and the line shows how to fix it.
- **"Kick doesn't show you live yet. Check the key and the channel."**: Corneta is sending, but the connected account's channel doesn't show the live. Check that the destination's key belongs to that same channel.

When the warning is about a setting, such as keyframes, bitrate, frame rate, resolution or audio, the line shows **Fix it now**. Corneta starts re-encoding just that destination until the live ends, with its preset's keyframes, bitrate and frame rate. The destination spends a few seconds in **Reconnecting**, and the PC uses more GPU or CPU. After that, the line says Corneta re-encodes the destination until the live ends; on YouTube, the warning can take a few minutes to clear. To keep it from coming back next time, open **How to avoid it in OBS**: the line shows where to change the setting in OBS. If Corneta already re-encodes the destination, the line asks you to adjust its preset in **Quality**. A connection warning, such as a slow upload, has no such button, because re-encoding doesn't fix the network.

The first check goes out about 20 seconds after the destination reaches **LIVE**. The warning that the live doesn't show up only comes after 45 seconds, because platforms take a while to list a new live. After that, Corneta asks again every 30 seconds on Twitch and Kick and every 5 minutes on YouTube, which limits checks with a quota. That's why, on YouTube, the line can take a few minutes to change after a fix. If the destination reconnects, the count starts over.

The line doesn't show up without a connected account, or when there are two destinations on the same platform, because the account shows a single channel.

## If the ingest server crashes

The ingest server is the part of Corneta that receives the OBS signal on your PC. If it crashes mid-stream, Corneta brings it back on its own: the destinations spend a few seconds in **Reconnecting**, OBS reconnects and the live carries on. With BE RIGHT BACK turned on, viewers see the BE RIGHT BACK screen in the meantime. Windows and the paired phone say **The ingest server is back**. The output that builds the BE RIGHT BACK screen also comes back on its own if it crashes.

If the ingest server crashes three times within two minutes, the live ends in **Error** with the message "The ingest server crashed — try again." Start the live again. If it happens again, ask for help with the safe diagnostics file, as explained below.

## Waiting doesn't mean OBS is disconnected from the WebSocket

The WebSocket lets Corneta set up and control OBS. The video signal arrives over local RTMP. The OBS button can show **Set up** while Corneta keeps waiting, because OBS hasn't started streaming yet.

## When to ask for help

Write down the exact status, the affected platform and the message shown. If there's an error ID or operation ID, copy it as text.

Never share your stream key, WebSocket password, token, local path or a screenshot with a credential. Use [export safe diagnostics](/en/help/reports-and-data/export-safe-diagnostic).
