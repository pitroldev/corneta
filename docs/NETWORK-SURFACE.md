# Network surface and integration limits

Reference for the 0.7.0 line. This guide describes implemented capabilities, not provider authorization or a promise of availability. Configuration and responsibilities: [CONFIGURATION.md](CONFIGURATION.md). Vulnerabilities: [SECURITY.md](../SECURITY.md).

## The three capabilities are independent

**Streaming video by URL/key is not the same as reading chat or having OAuth.** The program can send video to a destination without any integration with that service's account. Having OAuth does not guarantee moderation permissions either: the provider and the account's role still decide.

### Cinefy audience

When a Cinefy chat source is connected, Corneta also queries the concurrent viewers of the streams hosted on Cinefy itself. The counter feeds the interface and the local reports: audience curve, peak, average, title and start time as reported by the provider. It requires no login, no streaming preset and no PostHog. Collection follows the connected channels; it does not recover audience from before the connection.

Embedded players from Twitch, YouTube, Kick or another platform are identified; when available, their counter appears as external audience reported by the player. It is not attributed to Cinefy, nor added to the total or to the native audience metrics. Accumulated views, followers, unique viewers and retention are not inferred from concurrent viewers or messages.

Queries use the roughly 30-second cycle, with a per-channel cache and progressive backoff after failures. Unavailable data is left without a reading instead of becoming zero; a valid response with zero viewers is still zero. During a Cinefy failure, the live counter flags the total as partial and the total chart keeps a gap, without inventing a drop or a spike on recovery. These endpoints have no stable public contract, so the parser rejects ambiguous responses. Details and limits are in the [Cinefy audience collector](../src-tauri/src/platforms/cinefy/audience.rs).

### Deck mode: paired, but without TLS

Deck mode stays off until the user turns it on in Settings, and it only exists while the app is open. Pairing uses a single-use token that is valid for 2 minutes and travels in the `#` of the QR URL, so it does not appear in the HTTP request line. The phone shows a 4-digit code that the streamer checks and approves on the PC. Once approved, the device receives a random 32-byte secret; the PC keeps only its SHA-256 in the vault and records the device in the configuration (up to 8). Removing the device deletes the secret and drops the connection immediately.

The commands are a closed list: mark a moment, BE RIGHT BACK, mute the mic and switch the OBS scene, pause a platform, send to chat, title and game, button order, combos (up to 8 steps of these same actions, without going live or ending the stream), going live, ending the stream and the device disconnecting itself. Going live and ending the stream go through the main window, on the same path as the app's button. While a phone is connected, the app keeps its own obs-websocket connection for scenes and microphone.

**Traffic is HTTP/WS without TLS.** Anyone on the same network can read the live state, the chat and the device secret, and with that secret impersonate the phone until the device is removed. The private IP, `Host` and `Origin` checks prevent access from the Internet and DNS rebinding from pages open in the browser, but they do not protect against someone on the same Wi-Fi. Use it only on your home network, never on public Wi-Fi, do not forward the port on the router, and remove devices you no longer use. References: [`deck/mod.rs`](../src-tauri/src/deck/mod.rs), [`deck/net.rs`](../src-tauri/src/deck/net.rs), [`deck/pairing.rs`](../src-tauri/src/deck/pairing.rs), [`deck/actions.rs`](../src-tauri/src/deck/actions.rs).

### Table must not be presented as safe for public exposure

The relay uses rooms and a per-peer secret to prevent improper takeover of a `peerId`, but this **is not equivalent to strong room-entry authentication, account authorization or TLS for signaling**. The server accepts new participants through the `join` message; the per-queue limit is not a global connection/room limit. The app only accepts `MESA1` invites with `host:port` (no credentials, path or address of this machine), refuses to take a seat at a table that already has six participants and does not open connections beyond that limit, plus one OBS view per seat; the relay does not enforce these locks on a modified client.

WebRTC media uses DTLS-SRTP; this does not encrypt the signaling HTTP/WS. The defaults include STUN `stun.l.google.com:19302` and `stun1.l.google.com:19302`; P2P/ICE can reveal network addresses to peers. There is no managed TURN that guarantees connectivity across every NAT. Use only trusted networks/participants, do not publish real invites, do not forward the port on the router, and do not expose this relay directly to the Internet.

Before promoting Table for public scenarios, explicit authentication/authorization, a protected signaling transport, global/per-origin limits and abuse testing are required. Documenting this limit does not implement those protections. References: [`mesa.ts`](../src/lib/mesa.ts), [`studio.rs`](../src-tauri/src/studio.rs), [`studio.html`](../src-tauri/assets/studio.html).

## Setup API: token boundary

The current code provides `GET /api/v1/bootstrap`, `GET /api/v1/health`, `POST /api/v1/oauth/kick/exchange` and `POST /api/v1/oauth/kick/refresh`. These handlers do not persist user tokens; the tokens pass through the server's memory/response. Do not claim that “the server never sees tokens”. External logs/proxies must keep the same restriction of not recording bodies/credentials.

- Exchange: 20 attempts and refresh: 60 per origin, with independent counters per route and a fixed 60-second window **per instance**. Excess requests get `429` with `Retry-After`; IPv6 is grouped by /64 and requests without a trusted IP share each route's `unknown` origin.
- Default JSON body up to 8 KiB; PKCE verifier of 43–128 valid characters; callback compared against the exact allowlist.
- Requests to the token endpoint have a 12 s timeout, `cache: no-store` and refuse redirects. API responses have `Cache-Control: no-store` and `nosniff`.
- The limiter uses a local cache of up to 10,000 entries in every environment. It stores the count, the expiry and an HMAC-SHA256 key derived with a random 32-byte secret generated at startup, with no configurable secret, raw IP or tokens in the cache. It does not query remote storage. When capacity is exhausted it returns `503`/`Retry-After` for new entries, without evicting active counters.
- Restarts and new instances get fresh counters: the local limit is not global. Shared control in front of the instances requires an external WAF/edge covering both POST routes, hosts, aliases and normalized paths; the origin must not be reachable around that edge. Before distributing, check the actual configuration and the provider's regional scope, without promising that protection is already active or that there is a global quota.
- Outside Vercel, the proxy must overwrite the configured IP header and prevent direct access to Next. Trusting a client-sent `X-Forwarded-For` allows the origin to be spoofed; do not remove this boundary to “unblock” login.
- The broker does not create a Corneta account: possession of code + verifier/refresh token is verified by the provider. Rate limiting reduces abuse; it does not turn the public desktop client into a client capable of keeping an official secret.

Evidence and regressions: [Kick handlers](../web/app/api/v1/oauth/kick/exchange/route.ts), [refresh](../web/app/api/v1/oauth/kick/refresh/route.ts), [`http.ts`](../web/lib/server/http.ts), [`http.test.ts`](../web/lib/server/http.test.ts), [`rate-limit-core.ts`](../web/lib/server/rate-limit-core.ts), [`rate-limit-core.test.ts`](../web/lib/server/rate-limit-core.test.ts).

## Vault, sign-out and local files

Stream keys, OAuth tokens and advanced credentials use [`keys.rs`](../src-tauri/src/keys.rs). The official namespace is different from the contributor one. The vault does not protect against every program running under the user's account, nor does it turn a BYOK secret into a secret the computer's owner cannot access.

The logout commands try to remove the local credentials and the relevant caches; a vault failure must be shown as an incomplete cleanup, not as success. Uninstalling does not guarantee that those entries are removed. **The current logout does not guarantee remote revocation**: to remove the authorization at the provider, also use the apps/connections area of the account itself. Expiry/renewal follows the provider; a refresh failure may require logging in again. Do not promise that disconnecting locally invalidates already compromised copies of a token.

Reports/chat/recordings are local files that may contain names, messages, titles, events and the stream's image/audio. They are not automatically safe to attach to an issue just because the stream key is in the vault. Use artificial fixtures or review/redaction before sharing; never publish a real `.ndjson` file, video, Table invite or screenshot without checking it for personal data and credentials.

## Recovering automatic YouTube broadcasts

The flow in [`platforms/youtube/broadcast.rs`](../src-tauri/src/platforms/youtube/broadcast.rs) keeps the pending record in the vault until it confirms the remote state and the local cleanup. On stop, it tries to complete broadcasts in `live`/`testing`; it never deletes automatically, including after network, quota or authentication errors. Broadcasts in `created`/`ready` or still transitioning stay pending: check the matching broadcast in YouTube Studio and cancel the schedule if you will not use it. An old observation of the state does not authorize deleting a video.

If the creation response is lost before it returns the ID, the app blocks any further automatic creation until the broadcast is reviewed in Studio and explicitly confirmed through the **Recover YouTube** flow. When the ID is known, that confirmation does not discard it: the app must query again or complete the broadcast. Stopping the local output does not prove that the remote broadcast has ended. Manual credentials remain a separate path; check the channel before assuming it is live.

## Experimental integrations and change review

Reading through internal/public web endpoints (including Cinefy and parts of YouTube/Kick/Twitch) must not be presented as a stable official contract. The Cinefy adapter explicitly records this limitation. This does not demonstrate a terms violation, nor does it allow assuming unlimited support: the maintainer must follow the provider's documentation/requirements and disable or adapt any flow that stops being supportable.

Network/OAuth changes must include proportional tests: callbacks with an incorrect/expired state, port already in use, invalid refresh, callbacks outside the allowlist, large/slow bodies, local cache capacity/TTL, independent counters across instances, WAF/edge blocking, forged origin, local logout and separation of official/BYOK/contributor credentials. Do not run send/moderation tests on real channels without the owner's authorization.

Automated tests do not replace validating real flows. Contract changes require new verification proportional to the risk. Do not open ports, stream or publish just to check the documentation.
